# MVVM & Data Binding

Wind uses the Model-View-ViewModel (MVVM) pattern for UI. Game logic does not directly manipulate UI nodes; instead, UI documents bind to properties and commands declared on a `ViewModel`.

---

## 1. Defining a `ViewModel`

Create a class inheriting from `engine::ui::ViewModel` and register each member under the name the XML uses:

```cpp
#include <engine/ui/bindable.h>
#include <engine/ui/binding_id.h>
#include <engine/ui/command.h>
#include <engine/ui/view_model.h>

#include <string>

namespace game {

class HudViewModel : public engine::ui::ViewModel {
public:
    HudViewModel() {
        // Register properties and commands under their binding names
        property(engine::ui::intern("healthText"), healthText);
        property(engine::ui::intern("score"), score);
        command(engine::ui::intern("togglePause"), togglePause);
    }

    // Names bound from XML MUST be camelCase
    engine::ui::Bindable<std::string> healthText{"100 HP"};
    engine::ui::Bindable<int> score{0};

    // Commands bound to buttons
    engine::ui::MethodCommand togglePause;
};

} // namespace game
```

The XML refers to them as `{binding healthText}`, `{binding score}`, and `command="{binding togglePause}"`. A property is a `Bindable<T>`: a string is shown as it is, and a number is formatted as text (`std::to_string`, so prefer an `int` for a counter). A `Bindable<engine::AssetId>` feeds an `<Image source="{binding portrait}">`, and a numeric one drives `checked`, `scroll-y`, `pan-x`, `drag`, and similar attributes (the engine also writes back to them when the player drags a slider or scrolls). A `ViewModel` cannot be copied or moved, so keep it in a `std::shared_ptr` and give that pointer to the canvas as `data_context`.

> [!IMPORTANT]
> **Naming Rule:** View-model members bound from XML markup **must** be `camelCase` (e.g. `healthText`, `togglePause`), because the generated binder registers the member by that name. All other C++ functions and members stay `snake_case`.

A binding name that the view model does not register is skipped, and the rest of the document still binds. The engine logs the missing name once per canvas as a warning (`UI document <id>: ...`), so check `game.log` when a value does not show. A typo is silent in the build.

## 2. Generated Binders

When `asset_codegen` cooks a UI document (e.g. `assets/ui/hud.xml`), it writes a binder struct next to the document's `AssetId` in `<build>/generated/<game>/asset_ids.h`. The struct is named in PascalCase after the file (`hud.xml` gives `assets::ui::Hud`) and has a `bind()` that registers every `{binding ...}` the document uses, by the member name:

```cpp
// Generated by asset_codegen (abridged)
namespace assets::ui {
inline constexpr engine::AssetId hud{"..."};

struct Hud {
    static constexpr engine::ui::BindingId healthText = engine::ui::intern("healthText");
    static constexpr engine::ui::BindingId score = engine::ui::intern("score");
    static constexpr engine::ui::BindingId togglePause = engine::ui::intern("togglePause");

    template<typename T>
    static void bind(T& vm) {
        vm.property(healthText, vm.healthText);
        vm.property(score, vm.score);
        vm.command(togglePause, vm.togglePause);
    }
};
}
```

Call `bind()` in your view model's constructor instead of writing the `property`/`command` lines by hand. The members must exist under exactly those names, or the build fails to compile:

```cpp
#include <asset_ids.h>

class HudViewModel : public engine::ui::ViewModel {
public:
    HudViewModel() {
        assets::ui::Hud::bind(*this);
    }

    engine::ui::Bindable<std::string> healthText{"100"};
    engine::ui::Bindable<int> score{0};
    engine::ui::MethodCommand togglePause;
};
```

The generator never writes the view-model class or its members; that is your code. A document with an `<ItemsControl>` also gets a nested struct per list (named after the `items_source` path, `Hud::InventoryItems`) for the row view model ([HUD & Controls](HUD-and-Controls.md#3-lists-with-itemscontrol)). A binding path that is not a valid C++ name has its `.` and other characters turned into `_` in the member name.

## 3. Reacting to Changes

A `Bindable<T>` tells you when its value changes, so a game does not poll a value the document writes (a slider's `drag`, a `TextInput`, a `Checkbox`). Register one handler per bindable, usually in the view model's constructor or the panel that owns it:

```cpp
vm_->volume.on_changed([this](const float& fraction) { audio_.set_master(fraction); });
vm_->name.on_changed([this](const std::string& text) { rename(text); });
```

- The handler runs once per change, with the new value. `set` with the value it already holds is silent, and so is a drag that ends where it started.
- A write from C++ (`vm.volume.set(0.5f)`) and a write from the document (the player drags, types, or ticks) are both reported.
- It runs immediately, on the main thread, inside `set`; for a document write that is inside input handling. Do not destroy the view model or its canvas from the handler: record what happened and act on it later in a system.
- A new `on_changed` replaces the old handler; an empty `std::function` removes it. `BindableList` has no notification: it changes through `set` or `edit(fn)`, and each counts one version when the items differ afterwards.

## 4. Showing and Hiding with `if`

`if="{binding name}"` on any element reads a `Bindable<bool>`. While it is `false` the element is gone: it takes no space in the layout (its siblings close up), is not painted, and cannot be hovered or clicked, exactly like `display: none`. A stylesheet rule cannot show it again.

```xml
<Stack class="details" if="{binding detailsOpen}">
    <Label text="{binding detailsText}"/>
</Stack>
```

```cpp
engine::ui::Bindable<bool> detailsOpen{false};
```

Use it instead of a zero-or-one item `ItemsControl` or a `"none"`/`"flex"` string. `visibility: hidden` in CSS is the other way to hide an element; it keeps the space. A name the view model does not have is logged once and the element stays visible.

## 5. Positions and Sizes from Floats

Bind a `Bindable<float>` (or `int`) to a custom property and use it in a length. The number is pixels:

```xml
<Stack class="marker" var-x="{binding markerX}" var-y="{binding markerY}"/>
```

```css
.marker { position: absolute; left: var(--x); top: var(--y); width: 12; height: 12; }
```

```cpp
engine::ui::Bindable<float> markerX;
vm.markerX.set(12.5f);   // 12.5 px; no "12.5px" string
```

A custom property also works inside `calc(var(--x) + 4px)`. The unit is always pixels for a bare number; if you need `%` or `em`, bind a `Bindable<std::string>` (`"50%"`).

## 6. Updating Data from Game Systems

In your game systems or frame updates, change the `Bindable<T>` values directly:

```cpp
void hud_sync_system(engine::ecs::World& world, HudViewModel& vm) {
    const auto& player_stats = world.ctx<PlayerStats>();

    // The next bind pass copies the new value into the label
    vm.healthText.set(std::to_string(player_stats.current_health) + " HP");
    vm.score.set(player_stats.score);
}
```

Register the sync as a lambda system on `Schedule::Frame`, `Phase::Game` (the view model reference is captured from the game or panel that owns it). The engine rebinds every canvas each frame in `Phase::Bind`, copies only values that changed, and re-lays-out only when bound text changed.
